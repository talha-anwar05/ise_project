# ADR-004: Time-Triggered Processing, Deadline Calculation and Decoupled Notifications

**Status:** Accepted
**Date:** 2026-11-14
**Deciders:** Project team (all members)
**Related:** ADR-001 (Calendar & Scheduling, Notifications, Dashboard & Briefing modules), ADR-002 (outbox, conditional lock, compute on read)

## Context

- **ASR-5:**
  - All deadlines use the Administrator-configured Official academic time zone (C-04), while users see their local time.
  - Counters count calendar-date boundaries.
  - Blackouts move deadlines and pause counters, overdue durations and review countdowns. A newly added Blackout adjusts only unlocked deadlines (BR-07, BR-08, BR-11 to BR-14, BR-19).
  - Many outcomes happen with no user action:
    - deadline locks and Missed Check-ins;
    - reminders, which are re-targeted when someone is replaced;
    - overdue and escalation notifications, including the 3-day Administrator escalation (BR-16);
    - the Monday Morning Briefing, which still runs during Blackouts (EC-20).
- **ASR-1:** a deadline lock must take effect **at the deadline instant**, even if no background process has run yet (AC-05g case 3).
- **ASR-6:**
  - Records and locks must save even when email is disabled or failing (NFR-04, EC-15).
  - Urgent in-app notifications are immediate; email is optional (BR-22).
  - The Briefing must show the categories that loaded, name the one that failed, warn "partial data" and offer retry (FR-15, EC-14).
- **OQ-05:** an event can be both urgent and part of a Digest; the duplicate needs handling.
- **OQ-06:** the time zone, Blackout and reminder values are configuration and must not be hard-coded.
- **C-03:** no email provider is fixed.
- **C-06:** date and status rules must be changeable in one controlled place.

## Alternatives considered

1. **Shared Calendar & Clock module + lock state derived from time + reliable background jobs + transactional outbox.**
2. **Separate cron scripts per feature + email sent inside the user's request.**
3. **Timers held in application memory**, one per deadline.
4. **External message broker or workflow engine.**

Sub-options considered:
- **Briefing:** generated by a Monday job and stored, vs. assembled on demand when opened.
- **OQ-05 handling:** in scheduling, vs. inside the Notifications module.

## Decision

1. **Calendar & Scheduling module: the single time authority**
   - It owns the Official time zone, the Blackout calendar, effective-deadline calculation (original, revised and effective), counter and overdue calculation, and review countdowns.
   - Every module that needs a date rule calls this module's interface. **No other module does its own date arithmetic.**
   - It provides an **injectable Clock**. Production code uses the server clock; tests can set any instant (for example 11:59:59 PM, or the first day of a Blackout).
   - All values from OQ-06 come from Administrator configuration.
2. **State derived from time**
   - A Check-in is treated as **locked by deadline** as soon as the Clock passes its effective deadline, even before any job has run.
   - The conditional lock update in ADR-002 includes "before the effective deadline". So a late Start review or Representative submission loses to the deadline.
3. **Reliable background jobs**
   - A job runner stored in the database records due work: deadline-lock materialisation, Missed Check-ins, reminders, overdue and escalation notifications, the 3-day Administrator escalation, and Monday Briefing delivery.
   - Each job has a **unique idempotency key** (for example "Missed Check-in for Group G, week W"). Reruns and restarts therefore never create duplicates.
   - Jobs can be **cancelled or rescheduled** when a Blackout is added or a person is replaced (BR-14). Each job re-reads current state and the Calendar before acting.
   - Jobs use the same Calendar module and the same database transaction rules (ADR-002), including audit.
4. **Notifications decoupled through the outbox**
   - A business transaction that causes a notification writes, in the same commit:
     - the **in-app notification records**, so in-app delivery is immediate and independent of email;
     - an **outbox row**.
   - After commit, a dispatcher in the Notifications module reads the outbox and sends email through an **Email port**, with retries and backoff.
   - Email can be **disabled entirely** (globally or per user) without affecting any save. The email provider is a swappable adapter (C-03).
   - In-process domain events (ADR-001) published after commit only wake up the outbox dispatcher immediately; the outbox row itself is already committed inside the originating transaction (ADR-002), and the dispatcher also polls on a timer so no notification is lost on a crash.
5. **Monday Morning Briefing**
   - The Briefing is **assembled on demand** whenever a supervisor opens it, so it is always current. Each FR-15 category is loaded **independently**. If one fails, the Briefing shows the rest, names the failed category, shows a "partial data" warning and offers a retry for that category (EC-14).
   - A **scheduled Monday job** sends the Briefing notification (in-app, plus email if enabled), including during Blackouts (EC-20). Any email content is built with the same per-category assembler, so it handles a failed category the same way.
6. **OQ-05: urgent events that also appear in a Digest**
   - Handled inside the Notifications module. When an urgent event has already been sent, it is **flagged as already notified** in the Digest feed, so it appears as history rather than as a new alert.

## Rationale

- **One time authority** removes duplicated, inconsistent date logic. That is essential because Blackouts, time zones and calendar-date counters are the most error-prone rules, and C-06 requires controlled changes.
- **Deriving lock state from time** makes AC-05g case 3 hold whenever the job runs. The job only *records* what is already true; it does not *decide* it.
- **Durable, idempotent jobs** survive restarts and retries without duplicate Missed Check-ins or notifications. Cron scripts and in-memory timers cannot guarantee that.
- **The outbox** keeps email out of the transaction, so an email outage or slowdown never blocks a save (NFR-04, EC-15) or delays it past the 3-second NFR-01 target. In-app records are written in the same commit, so urgent delivery stays immediate.
- **An on-demand Briefing** is always current, which suits rules that change with Blackouts and decisions. The scheduled notification still delivers it on Monday. Loading each category separately is what makes partial results possible.
- **A broker or workflow engine** adds infrastructure that this load does not need. The ports in this design allow adding one later.

## Trade-offs / consequences

**Positive**
- Deadline behaviour is correct and testable at exact boundaries, through the injectable Clock.
- No duplicate side effects. Email failures are isolated. The email provider is swappable.
- A Blackout or threshold change takes effect immediately everywhere.

**Negative / risks**
- More upfront infrastructure: a job table, an outbox table, a dispatcher, and an idempotency-key scheme.
- **Two paths must agree:** state derived from time, and jobs that record it. Both must use the Calendar module, and tests must cover the window where the deadline has passed but the job has not run yet.
- Email is delivered eventually (seconds to minutes, depending on how often the dispatcher runs). This is acceptable because only in-app notifications must be immediate.
- An on-demand Briefing does real work each time it opens, which adds to ASR-8 load. Per-category queries must be indexed (ADR-002). If performance tests fail, caching can be added through a superseding ADR.
- The Monday email shows the Briefing at the moment it was sent. Opening the in-app Briefing later may show newer data. This is intended behaviour.
- Job polling intervals and retry limits are operational settings that still need agreeing; they affect only how quickly notifications go out, not correctness.
